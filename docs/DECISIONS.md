# Ключевые инженерные решения

Здесь — почему система устроена именно так. Краткая версия — в README.

## 1. План агента — данные, а не код

План — это список вызовов инструментов с аргументами (`PlanStep`), а не цепочка
if/else и не «модель сама всё сделает внутри одного промпта». Отсюда всё
остальное:

- план **можно показать человеку до выполнения** — видно, какие шаги предстоит
  сделать и зачем (`reason` обязателен);
- план **можно проверить**: инструмент существует, поля и типы аргументов
  корректны, ссылки указывают на реальные шаги;
- план **можно продолжить с места сбоя**: выполненные шаги лежат в базе, и
  повторов не будет.

Альтернатива — «одна большая функция, которая сама ходит по API» — быстрее
пишется, но делает невозможными подтверждение, продолжение и разбор инцидентов.

## 2. Валидация плана до выполнения, а не «попробуем и посмотрим»

Модель ошибается предсказуемо: придумывает несуществующий инструмент, кладёт
строку в числовое поле, ссылается на шаг, которого нет в плане. Поэтому план
проходит проверку **до** первого сетевого запроса:

| Проверка | Что ловит |
|---|---|
| инструмент в реестре | «магические» вызовы, которых нет в коде |
| имена полей по схеме | опечатки и выдуманные параметры |
| типы обычных значений | `"limit": "много"` |
| ссылки на существующие шаги | `$search.items` при отсутствии шага `search` |
| отсутствие циклов | план, который нельзя выполнить последовательно |

Если проверка провалилась — платформа **не** делает вид, что всё в порядке:
она переходит на детерминированный план и записывает причину в `notes`. В
дашборде это видно как «план построен кодом» с текстом отказа.

## 3. Детерминированный планировщик — не заглушка, а рабочая ветка

Изначально это было «на случай, когда нет ключа». По факту оказалось ценным
само по себе:

- **CI проверяет сквозной путь** без ключей, внешних API и Postgres — на каждом
  пуше и PR;
- **демо воспроизводимо**: одинаковый запрос даёт одинаковый план и результат,
  поэтому на вывод можно ссылаться в отчётах и тестах;
- **деградация понятна**: если провайдер LLM недоступен, платформа продолжает
  работать и честно помечает источник плана.

Числа при этом берутся из текста регулярками (`constraints.py`), а не из
«понимания» модели: цена «до 5000 ₽» и «20 товаров» — это факты, которые нельзя
доверять вероятностной модели, если их можно прочитать точно.

## 4. Ранжирование — код, LLM — выбор шагов

Соблазн отдать «выбери 5 лучших» модели велик, но подборка — это то, что человек
проверит и что должно объясняться. Поэтому скор считается формулой: цена (0.45)
+ рейтинг (0.30) + логарифм числа отзывов (0.25) + надбавка за совпадение с
требованиями из запроса. Каждая карточка несёт `why` — из чего сложилась оценка.

Логарифм для отзывов выбран специально: 20 и 2000 отзывов — разница огромная,
2000 и 4000 — почти никакая.

## 5. Подтверждение человека на точке невозврата

Отправка сообщения — единственный шаг, который нельзя отменить. Поэтому он один
помечен `requires_approval`, и выполнение останавливается: статус
`waiting_approval`, дальше — явное действие человека. Подтверждение записывается
**событием в базе**, а не флагом в памяти: воркер и API — разные процессы, и
перезапуск любого из них не должен терять решение человека.

## 6. События как единственный источник прогресса

Прогресс лежит в таблице событий с монотонным номером `seq`. SSE-эндпоинт
**опрашивает базу**, а не подписывается на шину в памяти процесса.

Почему: API и воркер разнесены по разным контейнерам, поэтому шина в памяти
между ними не работает, а Redis pub/sub ради прогресс-бара — лишняя
инфраструктура, которую пришлось бы ещё и защищать от потери сообщений. Опрос
базы стоит одного индекса, работает при любом числе воркеров и позволяет
клиенту переподключиться с `?after=<seq>`, не теряя историю.

Фронтенд всё равно переходит на REST-опрос, если SSE-соединение оборвалось
(прокси, перезапуск API): прогресс важнее способа доставки.

## 7. Очередь хранит только id задачи

Классическая ошибка — положить в очередь саму задачу. Тогда потеря элемента
очереди = потеря задачи. Здесь в очереди лежит только идентификатор, а состояние
живёт в базе: задачу можно поставить заново (`/retry`), взять другим воркером и
продолжить с последнего выполненного шага. Redis в этой схеме — не «чтобы было»,
а способ развести приём задач и их выполнение и масштабировать воркеров.

## 8. Один SQL и два драйвера вместо ORM

Платформе нужны четыре таблицы и десяток запросов. Разница между SQLite и
PostgreSQL сведена к плейсхолдерам (`?` → `$1`) и переводится одной функцией в
`PostgresDriver`. Это меньше кода, чем слой ORM, и позволяет запускать полный
набор тестов на SQLite, а перед выкаткой проверять настоящую связку
(`scripts/integration_check.py`).

Обратная сторона честно названа в README: сложные миграции схемы придётся писать
руками.

## 9. Демо-данные помечаются везде, где появляются

Инструмент поиска без внешнего API возвращает встроенный каталог — воспроизводимый
и детерминированный. Но в выводе всегда есть `source: "demo"`, этот флаг доходит
до результата задачи (`data.search.source`) и до текста сводки курсивом:
«источник данных — демонстрационный каталог». Сымитированная доставка отмечается
так же.

Причина простая: портфолио-проект с фиктивной выдачей, который выглядит как
работающая интеграция, — это обман, который обнаруживается на первой же встрече.
Честная пометка не уменьшает демонстрацию, но делает её проверяемой.
