## Компоненты

| Компонент | Ответственность | Где |
|---|---|---|
| API (FastAPI) | приём задач, статусы, SSE-прогресс, вебхуки, статика дашборда | `app/api/main.py` |
| Воркер | берёт id из очереди, строит план, исполняет шаги | `app/worker.py` |
| Планировщик | цель → план вызовов инструментов (LLM либо код) | `app/core/agent/planner.py` |
| Исполнитель | повторы, таймауты, порядок, подтверждение, отмена | `app/core/agent/executor.py` |
| Инструменты | доступ к внешнему миру: API, браузер, таблица, доставка, файлы | `app/core/tools/` |
| Хранилище | состояние задач и журнал событий | `app/infra/db.py` |
| Очередь | разведение приёма и выполнения | `app/infra/queue.py` |
| Сервис | связка «создать → запланировать → выполнить → сохранить» | `app/services/tasks.py` |

**Зависимости направлены внутрь.** `app/core/**` не знает ни про FastAPI, ни про
SQL, ни про Redis: планировщик и инструменты работают с pydantic-моделями. Поэтому
ядро запускается без базы, очереди и сети — именно это делает демо-прогон
(`python -m app.demo`) полноценной проверкой, а не упрощённой копией.

## Путь одной задачи

1. **Приём.** `POST /api/tasks` (или форма/вебхук) → запись в `tasks` со статусом
   `queued`, событие `task_created`, id ставится в очередь. API отвечает `202` сразу.
2. **Планирование.** Воркер берёт id, ставит `planning` и строит план:
   модель через tool calling либо (без ключа) детерминированный план по тексту
   запроса. Каждый вызов проходит проверку: инструмент существует, поля и типы
   аргументов корректны, ссылки указывают на реальные шаги. План сохраняется
   целиком — его видно в дашборде.
3. **Выполнение.** Исполнитель идёт по плану в топологическом порядке. Ссылки
   `$step.field` (и `{{step.field}}` внутри текста) разрешаются значениями уже
   выполненных шагов. У каждого шага: таймаут, до `AAP_STEP_RETRIES` повторов с
   ростом паузы, запись результата в базу сразу после выполнения.
4. **Подтверждение.** Шаг, уходящий наружу (`send_report`), останавливает
   выполнение: статус `waiting_approval`, событие `approval_required`.
   `POST /api/tasks/{id}/approve` записывает событие `approved` и возвращает id в
   очередь; воркер продолжает **с этого шага** — выполненные шаги не повторяются.
5. **Результат.** Сводка, таблица (markdown + CSV), артефакты и данные доставки
   сохраняются в `result`. Событие `task_finished` закрывает прогресс, SSE-поток
   завершается.

## Состояния

```
queued ──▶ planning ──▶ running ──┬──▶ done
   │           │            │     ├──▶ waiting_approval ──▶ running ──▶ done
   │           │            │     └──▶ failed ──▶ (retry) ──▶ queued
   └───────────┴────────────┴──▶ cancelled
```

Переходы описаны в `app/core/state.py` и проверяются на каждом изменении:
отменить завершённую задачу нельзя (API вернёт `409`), а повторный запуск
`failed` — можно. В базе статус меняется только через эту проверку, поэтому
нельзя получить «выполняется» после «готово».

## Где что лежит

```
app/
├── api/main.py         REST + SSE + статика дашборда
├── worker.py           цикл воркера (--once для тестов и CI)
├── demo.py             сквозной прогон без ключей, сети и баз
├── core/
│   ├── models.py       Task, Plan, PlanStep, StepResult, TaskResult, TaskEvent
│   ├── state.py        машина состояний
│   ├── config.py       настройки из окружения (AAP_*)
│   ├── formatting.py   единое форматирование чисел и денег
│   ├── agent/
│   │   ├── planner.py      LLM-план + детерминированный план + валидация
│   │   ├── executor.py     выполнение, повторы, подтверждение, отмена
│   │   ├── refs.py         ссылки между шагами, топологический порядок
│   │   ├── constraints.py  разбор цели (числа, цена, требования, доставка)
│   │   ├── llm.py          OpenAI-совместимый клиент с tool calling
│   │   └── prompts.py      системные промпты
│   └── tools/          search_products, rank_products, open_page,
│                       build_table, save_artifact, send_report
├── infra/
│   ├── db.py           SQLite и PostgreSQL за одним SQL
│   └── queue.py        память и Redis за одним протоколом
└── services/tasks.py   склейка всего: create → process → resume → cancel
```

## Развёртывание

| Режим | База | Очередь | Команда |
|---|---|---|---|
| Локально / демо | SQLite | в процессе | `python -m app.demo` |
| Разработка | SQLite | в процессе | `uvicorn app.api.main:app --reload` |
| Прод | PostgreSQL | Redis | `docker compose up --build` |

Прод отличается от разработки только двумя переменными окружения
(`AAP_DATABASE_URL`, `AAP_QUEUE`) — код один и тот же, ветвлений по среде нет.

## Метрики и наблюдаемость

- `GET /health` — статус, режим хранилища и очереди, режим планировщика;
- `GET /api/stats` — число задач по статусам, шагов, событий;
- журнал событий задачи — единственный источник правды о том, что произошло:
  он переживает перезапуск процесса и используется и дашбордом, и разбором сбоев;
- в каждом результате указан `data.plan_source` (кто строил план) и
  `data.search.source` (`api` или `demo`) — отчёт нельзя принять за прод-данные.
